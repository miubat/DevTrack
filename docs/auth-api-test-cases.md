# Auth API test cases · DevTrack · AGL-06.6

Test cases for the authentication API built in AGL-06 (login, refresh, logout, access token, roles, lockout and rate limit). They cover FR-AUTH-01, FR-AUTH-02 (deactivation only), FR-AUTH-04, NFR-SEC-01, NFR-SEC-02, NFR-SEC-05, NFR-SEC-07, the role rules in SRS §1.3 and the error codes in SRS §5.3. AGL-34.2 automates the cases in `backend/test/auth-*.e2e-spec.ts`.

**Not covered yet**

- FR-AUTH-02 (user administration) and FR-AUTH-03 (profile and password): their APIs are not built yet. Only the effect of deactivation (FR-AUTH-02) is tested, in cases 08 and 16, by changing the user with SQL.
- Project membership and ID tampering (NFR-SEC-03, NFR-SEC-04): they need the project and issue APIs (AGL-34.3).

**Environment**

- Build: master c1b0396. Backend on `http://localhost:3000` with the seeded database (`npm run db:setup` in `db/`).
- Seed users, all with password `Passw0rd1`: admin@devtrack.local (ADMIN), rahim@devtrack.local and sadia@devtrack.local (PROJECT_MANAGER), karim@, hasan@, nila@, imran@, tania@devtrack.local (TEAM_MEMBER).
- Tool: curl (on Windows, call `curl.exe`, not the PowerShell `curl` alias).

**How to read the Expected column**

- The source is in brackets at the end of each line, e.g. "(FR-AUTH-01)". "SRS silent" means the SRS and the tickets do not define it; the observed behaviour is in Actual.
- SRS §5.3 puts every route under `/api/v1`, e.g. `/api/v1/auth/login`. Expected uses the SRS path; Actual gives the path the build really serves. `/auth/me` and `/access-check/*` are not in the SRS (test routes from AGL-06.4 and AGL-06.5).

**Before you run**

- The login limit is 10 requests per minute per IP (case 29). Cases 26, 28 and 29 start with "wait 1 minute or restart the backend", so they do not affect each other.
- The lockout cases (26 to 28) leave rows in `failed_logins`. Clear them afterwards: `DELETE FROM failed_logins;`
- Cases 08 and 16 deactivate a user with SQL. Set the user back to active after the case.

## Test runs

**Run 1 · 2026-11-23** · Tester: Sanzida Khan Mitu (QA 2) · master c1b0396, local backend (`npm run start:dev`) and Docker database with seed data · curl in Git Bash on Windows

- All 29 cases at the time were run. They were marked as passed, but the Expected column then had no SRS §5.3 error codes and case 16 had no access-token step.
- The first login returned 500 because the local `backend/.env` had an old `DATABASE_URL`. After copying the value from `backend/.env.example` and restarting the backend, it worked. This was a local setup problem, not a product bug.
- Tokens for cases 19 and 20 were made in the `backend` folder with the `jsonwebtoken` package (in Git Bash, call `node.exe`, not `node`, inside `$( )`):
  - Case 19: `node.exe -e "require('dotenv').config(); console.log(require('jsonwebtoken').sign({sub:'1',role:'ADMIN',exp:Math.floor(Date.now()/1000)-60}, process.env.JWT_ACCESS_SECRET))"`
  - Case 20: `node.exe -e "console.log(require('jsonwebtoken').sign({sub:'1',role:'ADMIN'}, 'someone-else-secret', {expiresIn: 300}))"`
- Cookies for the session cases were kept with `curl -c <file>` and sent with `curl -b <file>`.
- After the run: Tania and Nila were set back to active, and `failed_logins` was cleared.
